--------------------------------------------------------------------------------
OVERVIEW
--------------------------------------------------------------------------------

Build a web-based crew availability calendar for a 16-person wildland fire crew
in Eastern Kentucky. This replaces a Google Form that gets sent out weekly asking
crew members which weekend days they can work. The goal is a single shared URL
that the whole crew can visit, sign up for days they're available to work, and
see who else has signed up. No login, no admin panel, no separate views — just
one live collaborative sign-up sheet that everyone can read and edit.

This is a STANDALONE project for now, but it must be built modularly so it can
later be integrated as a module into a separate existing project called
"Fire Radar" (EKY Fire Radar dashboard). Build with clean separation between
frontend and backend so components can be lifted and dropped into another
project with minimal rework.

--------------------------------------------------------------------------------
TECH STACK
--------------------------------------------------------------------------------

- Frontend: Plain HTML + CSS + vanilla JavaScript (no frameworks)
- Backend: Cloudflare Worker (handles all API requests)
- Database: Cloudflare D1 (SQLite-based, stores sign-up entries)
- Hosting: Cloudflare Pages (static frontend deployment)
- Deployment pattern: Cloudflare Pages via zip upload

Do NOT use Firebase, Supabase, or any third-party database. Keep everything
inside the Cloudflare ecosystem. The developer is already familiar with
Cloudflare Pages zip upload deployments and Cloudflare Worker development.

--------------------------------------------------------------------------------
CORE FEATURE: THE CALENDAR
--------------------------------------------------------------------------------

The calendar shows only Saturdays and Sundays that fall within Kentucky's two
wildland fire seasons:

  Spring season: February 15 – April 30
  Fall season:   October 1 – December 15

Days outside these seasons are NOT shown at all. The calendar should display
all upcoming fire season weekends from today forward through the end of the
current or next active season. Past dates within the season should remain
visible but be locked (cannot add or remove names).

The calendar layout should be clean, scannable, and mobile-first. Each
weekend should show Saturday and Sunday together as a pair. For each day,
show the date and a list of crew member names who have signed up. A crew of
up to 16 people might sign up for any given day, so the name list needs to
be readable even when full.

--------------------------------------------------------------------------------
SIGN-UP INTERACTION
--------------------------------------------------------------------------------

Adding a name:
- User clicks on a day (or a clearly labeled "Sign up" button on that day)
- A simple modal or inline input appears asking for their name
- They type their name and confirm
- Their name appears on that day immediately (optimistic UI update, then
  confirm with backend)

Removing a name:
- User clicks on any existing name in the list
- A confirmation dialog appears: "Remove [Name] from [Day, Date]? Yes / Cancel"
- On confirm, the name is removed
- This is fully trust-based — anyone can remove any name. The confirmation
  dialog is just to prevent accidental deletions.

There is NO login, NO authentication, NO admin role. The entire system is
honor-based. Keep the interaction as low-friction as possible. The crew
members using this are field workers on phones, not office workers on desktops.

--------------------------------------------------------------------------------
DATA MODEL (D1 SCHEMA)
--------------------------------------------------------------------------------

One table is sufficient:

  CREATE TABLE signups (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    date TEXT NOT NULL,          -- ISO format: YYYY-MM-DD (always a Sat or Sun)
    name TEXT NOT NULL,
    created_at TEXT DEFAULT (datetime('now'))
  );

No duplicate names per day — enforce this at the application level (check
before inserting, show a friendly message if name already exists on that day).
Case-insensitive duplicate check is fine (e.g. "Ben" and "ben" = same person).

--------------------------------------------------------------------------------
WORKER API ROUTES
--------------------------------------------------------------------------------

GET  /api/signups?date=YYYY-MM-DD    Returns all signups for a specific date
GET  /api/signups/range?start=YYYY-MM-DD&end=YYYY-MM-DD   Returns all signups
                                     within a date range (used on page load to
                                     fetch the whole season at once)
POST /api/signups                    Body: { date, name } — adds a signup
DELETE /api/signups                  Body: { date, name } — removes a signup

All responses should be JSON. Include proper CORS headers on all responses
so the frontend (served from Pages) can talk to the Worker without issues.

--------------------------------------------------------------------------------
DESIGN GUIDELINES
--------------------------------------------------------------------------------

- Mobile-first. Most crew members will use this on their phone.
- Dark theme preferred — this crew works outdoors and a dark UI is easier
  on the eyes in bright conditions and at night.
- Typography should be large and readable. Don't make people squint.
- Color accent: use a fire/ember color palette — deep oranges and ambers on
  a dark background work well thematically and visually.
- Each weekend pair (Sat + Sun) should be visually grouped together.
- Show the month and date clearly on each day tile.
- Name lists on each day tile should be compact but readable.
- Empty days should look inviting, not broken — something like "No one yet —
  be the first!" or similar friendly placeholder.
- Keep the UI simple. No charts, no graphs, no statistics. Just the calendar
  and the names.
